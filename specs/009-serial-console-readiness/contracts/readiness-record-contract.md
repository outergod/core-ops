# Contract: Serial Console Readiness Record

## Purpose

Defines the guest-published readiness record consumed by the VM-backed CoreOps
verification harness.

## Contract Shape

The guest emits exactly one structured readiness line on the serial console for
normal successful readiness establishment.

```text
CORE_OPS_VERIFY_READY {"run_id":"run-123","token":"abc123","ip":"192.0.2.10","hostname":"vm-1","ts":"2026-04-07T00:00:00Z"}
```

## Required Fields

- `run_id`: identifier for the current verification run
- `token`: run-scoped token generated by the harness
- `ip`: usable guest IPv4 address for later guest-boundary steps

## Optional Fields

- `hostname`: guest hostname for diagnostics
- `ts`: guest timestamp for diagnostics

## Contract Rules

- The line MUST begin with the stable marker `CORE_OPS_VERIFY_READY `.
- The JSON object following the marker MUST be parseable as a single complete
  object.
- `run_id` MUST match the current verification run.
- `token` MUST match the current verification run token.
- `ip` MUST be a usable IPv4 address.
- The harness MUST reject records that are malformed or that do not match the
  current `run_id` and `token`.
- The harness MUST use the `ip` from the first accepted record as the
  authoritative guest address for later guest-boundary work.
- If later readiness records for the same `run_id` and `token` appear after
  acceptance, the harness MUST ignore them for guest selection and retain them
  only as diagnostic evidence.
- During migration, fallback discovery MAY remain available, but it MUST NOT
  outrank a valid accepted readiness record.

## Failure Semantics

- Missing valid record before the readiness deadline: timeout or
  infrastructure-style readiness failure.
- Malformed record: rejected and logged as malformed readiness evidence.
- Mismatched `run_id` or `token`: rejected as stale or unrelated readiness
  evidence.
- Accepted record followed by later SSH or guest-command failure: later failure
  remains distinct from readiness acquisition success.

## Compatibility Notes

- The readiness record is an internal harness-facing runtime contract, but it
  materially affects externally observable verification behavior and failure
  semantics.
- The implemented rollout policy keeps stable `core-ops` operator flags
  unchanged while evolving `core-ops-verify` runtime behavior and machine-
  readable run semantics conservatively; compatibility review remains required
  for marker, field, and failure-class changes.
- Additive optional fields SHOULD preserve the stable marker and required field
  meanings.
- Changes to the marker, required fields, identity matching rules, or address
  semantics require conservative compatibility review.
