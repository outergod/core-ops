# Phase 0 Research: Serial Console Readiness

## Decision 1: Use guest self-report on the serial console as the primary readiness path

- **Decision**: Treat a guest-published serial-console readiness record as the
  primary readiness and guest IPv4 discovery mechanism for VM-backed
  verification runs.
- **Rationale**: The current ARP-first path is timing-sensitive and depends on
  neighbor-cache visibility rather than the guest's actual readiness. A
  guest-published record gives the harness an explicit contract tied to the
  guest lifecycle and already fits the existing console-log artifact path.
- **Alternatives considered**:
  - Continue relying on `virsh domifaddr` with ARP/lease probing: rejected
    because it preserves the known flakiness this feature exists to remove.
  - Shared guest-to-host file channel: rejected because it adds additional
    plumbing and surface area beyond the existing console-log path.

## Decision 2: Bind readiness to both run id and token

- **Decision**: Require the readiness record to carry both the current run id
  and a run-scoped token generated by the harness.
- **Rationale**: The run id alone may be human-readable and potentially reused
  in logs or artifacts; adding a run-scoped token makes stale-record rejection
  more robust and keeps the trust boundary explicit.
- **Alternatives considered**:
  - Run id only: rejected because it weakens stale-data rejection in the
    presence of reused log locations or copied console output.
  - Hostname only: rejected because hostnames are not sufficient to bind
    readiness to one verification run.

## Decision 3: Keep the readiness payload to a single structured line

- **Decision**: Emit exactly one structured readiness line containing run id,
  token, IPv4 address, and optional hostname/timestamp diagnostics.
- **Rationale**: A single-line contract is easy to parse, survives console-log
  capture cleanly, and minimizes ambiguity about which console event actually
  establishes readiness.
- **Alternatives considered**:
  - Multi-line readiness blocks: rejected because they complicate parsing and
    increase the chance of partial or interleaved console data.
  - Human-oriented unstructured log text: rejected because it weakens
    automation and makes malformed-data handling ambiguous.

## Decision 4: Inject the guest readiness payload through the existing Ignition path

- **Decision**: Extend the existing Butane/Ignition rendering path to install a
  readiness script and oneshot service into the guest.
- **Rationale**: `src/io/libvirt.rs` already renders and ships Ignition for
  VM-backed verification guests. Reusing that path keeps the new behavior
  inside existing provisioning boundaries and avoids introducing repo-under-test
  changes.
- **Alternatives considered**:
  - Post-boot SSH bootstrap: rejected because it requires the very guest
    connectivity this feature is trying to establish.
  - Modifying scenario fixtures or managed repos: rejected because readiness is
    a harness concern, not a scenario-under-test concern.

## Decision 5: Scope the first version to IPv4 only

- **Decision**: The readiness record only needs to provide a usable IPv4
  address in this feature.
- **Rationale**: The current verification harness, libvirt environment, and
  SSH path already assume IPv4 connectivity in the common case. IPv4-only keeps
  the contract narrow and directly solves the current reliability problem.
- **Alternatives considered**:
  - Accept either IPv4 or IPv6: rejected for now because it broadens the
    address-selection contract and test matrix without being required by the
    current harness.
  - Require dual-stack reporting: rejected because it adds scope with no
    immediate operator value for the current environment.

## Decision 6: Keep ARP only as a temporary migration fallback

- **Decision**: Preserve ARP-based discovery only as a temporary fallback during
  rollout, and only after valid serial-console readiness has not been obtained.
- **Rationale**: This lowers rollout risk for real environments while still
  making the new readiness record the authoritative contract.
- **Alternatives considered**:
  - Remove ARP immediately: rejected because rollout risk is higher when a new
    readiness path has not yet proven itself across all existing hypervisor
    setups.
  - Keep ARP permanently as an equal peer: rejected because it would weaken the
    clarity of the new contract and allow the old unreliable behavior to remain
    first-class.

## Decision 7: Missing or invalid readiness remains an infrastructure-style failure

- **Decision**: Missing, malformed, or stale readiness records should map to
  explicit readiness timeout or infrastructure-style failure outcomes rather
  than behavioral CoreOps assertion failures.
- **Rationale**: Readiness acquisition happens before the harness can exercise
  the guest's behavioral claims, so failure belongs to environment access and
  orchestration rather than the CoreOps behavior-under-test layer.
- **Alternatives considered**:
  - Map readiness failures to assertion failure: rejected because it would blur
    harness-access problems with product behavior regressions.
